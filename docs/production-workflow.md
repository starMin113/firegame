# 项目制作与验证工作流

日期：2026-11-03。状态：首版制作基线；后续按验证结果修订。

## 目标与当前事实

本项目以商业化为长期目标，以消防资源调配和连续灭火的解压感为核心。当前阶段要证明核心体验、内容生产和工程基础是否值得继续投入，不把五关 Demo 当作可商业发布产品。

已存在：五关 Web 原型、正式设计文档、30 关纸面母题测试、Unity 2022.3.20f1c1 / URP 14.0.10 工程。

尚未完成：Unity 可玩版本、目标玩家外部验证、正式美术方向、屏幕方向验证、目标设备性能测量、发行与变现方案。MCP 包已安装不等于编辑器连接已验证。

## 文档与决策来源

- `game-design.md`：已确认的玩法规则。旧标题中的“已落地”指 Web 原型，不能据此判断 Unity 实现状态。
- 本文：阶段与交付流程。
- `unity-first-slice.md`：当前实现方案和任务状态；技术建议不自动成为已确认产品需求。
- 讨论记录和 30 关表：候选想法与素材，不自动进入待开发范围。

决策记录至少写明日期、问题、结论、依据、尚未验证之处，以及受影响的文档或代码。用户拥有产品取舍权；Codex 提出技术与体验建议，说明异议和证据，不把每项实现细节交给用户决定。

## 阶段与通过条件

| 阶段 | 交付 | 通过条件 | 未通过时 |
| --- | --- | --- | --- |
| A 预制作 | 屏幕布局对比、一张含 UI 的游戏画面样稿、技术方案 | 目标屏幕下信息清晰、操作空间可用；方案能支撑规则和撤销 | 修改方案，停止批量资产生产 |
| B 第一关切片 | 简化场景、美术反馈、完整操作和可运行构建 | 核心流程可靠，连续灭火反馈成立；实际试玩找不到阻断问题 | 优先修操作、信息或反馈，不扩关掩盖问题 |
| C 五关验证 | 五种决策、关卡配置、试玩记录 | 新玩家能理解规则；能区分关卡决策和重复劳动，列出继续或调整的证据 | 调整数值、教学或核心设计 |
| D 制作验证 | 新一组关卡、配置验证工具、真机报告、制作耗时 | 可以稳定制作、验证和修改关卡，内容成本与表现成本有记录 | 改工具、缩范围或调整内容策略 |
| E 商业验证 | 选定市场和渠道、合法合规方案、必要数据与变现实验 | 有真实用户数据支持下一阶段投入，成本和风险可解释 | 暂缓扩产，回到相应假设 |

以上阶段是项目决策点，不是固定周数承诺。完成代码不等于阶段通过。任何“好玩”“留存可行”“性能足够”的结论都要标注证据及样本限制。

## 当前范围

本轮制作范围是五关核心验证。包含有限水车、无限消防栓、可回收有限水管、灭火器、静态火点、隐藏资源、水源开关、传播和撤销。

不加入消防站经营、养成经济、广告 SDK、支付、账号、联网服务、动态蔓延、天气、增压泵、人员救援和评分。这些不是取消的商业方向，而是当前尚无必要验证的系统。

早期五关不绑定商业化经济：不为广告或付费刻意制造资源困局，不让未接入的商业系统干扰核心体验结论。

## 单项任务流程

1. 定义问题、范围、验收条件、依赖和是否影响既有规则。
2. 检查现有实现与工程状态，先处理会使结果不可信的编译或资源问题。
3. 用最小可维护实现完成任务；涉及范围变更先记录取舍。
4. 完成与风险匹配的验证。规则、资源和撤销需要自动化回归；纯布局与表现需要实际画面检查。
5. 更新实现状态、验证结果、已知问题；形成可审查的 Git 差异。
6. 按明确授权提交或发布。内部交付默认提供本地结果；不因“完成任务”自动推送远端、覆盖线上版本或提交商店。

每个任务记录：编号、目标、状态、验收、结果。状态用待开始、进行中、待验证、完成、阻塞。待验证不能记作完成。

## Git 与可复现工程

- 唯一项目仓库是当前 `firegame`，不使用外层目录的 Git 仓库管理项目。
- 功能开发默认使用 `codex/` 前缀分支；开始前检查并保留用户未提交工作，不擅自清理、覆盖或合并。
- 主分支保持可打开、可编译；每个阶段留有明确提交标识及可运行构建。
- 提交 `Assets` 及对应 `.meta`、`Packages`、`ProjectSettings`、源码与文档。忽略缓存、用户设置、生成工程文件、凭据和构建输出。
- Unity 使用文本序列化与可见元文件；移动资产保留 `.meta`。修改场景前确认未保存状态。
- 依赖固定版本；记录来源、版本、授权和用途。升级单独验证，避免与玩法大改混在一起。
- 新电脑通过仓库和记录的 Unity 版本恢复；恢复检查应包含打开工程、依赖解析、编译和首关运行。
- MCP 属于开发工具，不得成为玩家构建的运行依赖。

## 质量与验证

功能验收：成功通关、资源不足、停水、撤销、重置、输入取消、隐藏信息恢复及重复操作均有明确结果。

关卡验收：至少一条有效解法；没有意外软锁；资源限制产生可理解的选择。记录水量余量、同时用管峰值、关键顺序、隐藏线索和重复铺管量。不能用“能解”代替“值得玩”。

体验验收：区分通水前后管道、明确水源开关、火点和资源需求，检查同格遮挡及手指覆盖。一次正确操作应产生及时且连贯的反馈。

性能验收：先确定代表性低端设备与帧率目标，再测 CPU/GPU 帧时间、内存、加载与发热。新增 Update、计时器、轮询或持续特效前，说明位置、频率、实例范围、单次工作、必要性及是否已实测；交付汇总持续执行点。当前没有性能合格结论。

试玩先让目标玩家独立操作，避免作者讲解掩盖教学问题。记录困惑位置、误触、提示依赖、撤销原因、是否愿意继续和清场感受；区分观察事实与玩家口头评价。录屏及数据收集先取得知情同意。

## 构建与发布记录

每个可分发版本记录：版本号、Git 提交、Unity 版本、平台、关卡范围、验证设备、已知问题及包位置。验证包标明测试用途。

接入商业 SDK、公开推广或商店提交前，再落实目标国家/地区、渠道规则、隐私和年龄要求、素材授权、数据采集、付费或广告体验及运营支持。届时以最新官方要求核查，不把当前流程文档视为法律或平台合规结论。
